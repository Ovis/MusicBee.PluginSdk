# Q001-Q030 MusicBee API Audit

最終更新: 2026-08-31

この文書は、設計Decision Q1-Q30についてMusicBee 3.6の実API・公式資料との整合性を監査した結果を記録する。

## 監査方針

- 一次資料は現行公式 `MusicBeeInterface.cs` を最優先する
- 一次資料だけで意味論が分からない場合は、MusicBee作者StevenによるForum回答を優先する
- 実APIで確認できない設計上の選択は `Design-only` とする
- 実動作が必要な項目は `Needs test` とする
- 既存Decisionと実APIが衝突する場合は `Needs correction` とし、別Qで補正する

## 公式API上の重要な事実

- 現行 `MusicBeeInterface.cs` は `MinInterfaceVersion = 43`、`MinApiRevision = 57`
- `ApiRevision >= 58` は `MusicBeeVersion.v3_6` と判定される
- Pluginは `MusicBeePlugin.Plugin` partial classという形を前提にしている
- Plugin typeは General / LyricsRetrieval / ArtworkRetrieval / PanelView / DataStream / Storage / VideoPlayer / DSP / TagRetrieval / TagOrArtworkRetrieval / Upnp / WebBrowser 等
- `PluginInfo` は Type / Name / Description / Author / TargetApplication / Version / MinInterfaceVersion / MinApiRevision / ReceiveNotifications / ConfigurationPanelHeight を持つ
- `PluginStartup` notificationは「successful initialisation後」に送信される
- MusicBee作者は、実際のstartup処理を `Initialise()` ではなく `PluginStartup` notification側へ置くよう案内している
- Notification callbackはMusicBee GUI threadとは別threadから呼ばれる
- MusicBee作者は、そのthreadからMusicBee APIを呼ぶこと自体には問題ないと説明している
- `PluginCloseReason` は MusicBeeClosing / UserDisabled / StopNoUnload
- ReceiveNotificationFlagsは StartupOnly / PlayerEvents / DataStreamEvents / TagEvents / DownloadEvents
- API interfaceはbackwards compatibleと公式Forumで案内されている

- Q16 — **Design-only**
- Q17 — **Design-only**

- Q19 — **Design-only**

### Q21-Q23

- Q21 .NET event + DI Event Handler — **Design-only / Compatible**
  - MusicBeeは単一 `ReceiveNotification` callbackへ通知するため、Framework内部でfan-outする設計は可能
- Q22 error semantics null/Try/Exception — **Design-only**
- Q23 normal lifecycle + optional interfaces — **Partially verified**

### Q24-Q27

- Q24 Source Generatorでentrypoint生成 — **Design-only / Compatible**
  - 公式が固定namespace/class/method形状を要求するためgeneratorの価値がある
- Q25 metadata Attribute + Startup — **Design-only / Compatible**
- Q26 `IMusicBeePluginStartup` — **Design-only**
- Q27 SDK service Singleton — **Design-only**

### Q28-Q30

- Q28 APIは同期/no switch、Frameworkがmarshal mechanism提供 — **Needs correction**
  - NotificationはGUI threadとは別threadで呼ばれる
  - ただしMusicBee作者はnotification threadからMusicBee APIを呼ぶこと自体には問題ないと説明している
  - よって `IMusicBeeDispatcher` を「MusicBee API呼び出しをMusicBee threadへmarshalするための必須機構」と位置付けるのは実態と合わない
  - UI/WinForms control操作などthread affinityが必要な用途に限定するか、dispatcher自体の責務を再定義すべき
- Q29 `IMusicBeeDispatcher` — **Needs correction together with Q28**
- Q30 MusicBee 3.6 series support — **Verified direction**
  - 現行interfaceはApiRevision 58以上をv3.6として扱う
  - exact minimum patch/buildをSDKが保証するかは別途決定可能

## 監査で新たに確定した実装上の方向

Framework lifecycleは少なくとも次のように分ける方向がMusicBee実態に合う。

1. `Initialise(IntPtr)`
   - API interface取得
   - PluginInfo返却
   - Frameworkの最小bootstrapのみ
   - 長時間のapplication startup処理を行わない
2. `NotificationType.PluginStartup`
   - DI application lifecycleの `StartAsync` 開始点候補
   - MusicBee作者の推奨とも一致
3. `Close(PluginCloseReason)`
   - `StopAsync` bridgeの開始点候補
   - timeout / blocking方法は実機検証が必要

## 要判断

Q28/Q29のdispatcher責務を補正する必要がある。

## 要実機検証

- net48 Plugin DLLをMusicBee 3.6最新buildが問題なくloadすること
- `Initialise` / `PluginStartup` / `Close` の呼び出しthreadと順序
- `Close` callback中にどの程度待機可能か
- `Configure` / `SaveSettings` callbackのthread
- Plugin disable/re-enable時の `PluginCloseReason` とassembly unload挙動
